## 1. 文档目的

本说明书用于指导 Claude Code 在**不破坏现有数据、模型和接口契约**的前提下，完成“EcomNLU · 智购感知”的 Web 前后端制作。

本轮交付重点是可在答辩现场稳定演示的单页应用：用户输入一条电商评论，选择 Top-K，调用真实模型，查看预测类别、置信度、Top-K 概率、模型名称、推理耗时、情感状态和建议处理方式。

图片仅作为视觉与布局参考。图片中的示例概率、模型名称、耗时和预测结果均为展示数据，**不得写死到代码中，也不得当作真实实验结果**。

## 2. 当前项目事实与边界

### 2.1 已有能力

当前后端已经具备：

- `GET /api/health`：返回服务、模型和情感任务状态。
- `GET /api/categories`：返回固定 10 类类别列表。
- `POST /api/predict`：接收评论和 Top-K，返回类别预测结果。
- 模型在服务启动阶段通过 `load_predictor()` 加载一次，请求阶段不重复加载。
- 模型未就绪时服务仍可启动，健康检查返回 503，预测返回 `MODEL_NOT_LOADED`。
- API 的正常、异常和未加载模型路径已经有自动化测试。

### 2.2 本轮必须完成

- 新增可直接访问的前端页面，并由现有 FastAPI 服务托管。
- 页面完整接入已有 API，不创建第二套预测逻辑或接口格式。
- 正常状态、加载状态、空状态、模型未加载和服务异常状态均有明确 UI。
- 使用真实 API 返回值展示类别、概率、耗时和模型名称。
- 增加前端测试与静态资源路由测试，并完成一次真实模型端到端验证。
- 更新 README 的启动方式、页面地址和验证步骤。

### 2.3 本轮不做

- 不重新训练、修改或提交大型模型权重。
- 不改变 `docs/contracts.md` 已冻结的请求、响应字段和错误码。
- 不实现账号、登录、数据库、云部署和外部大模型 API。
- 不伪造 M5 情感结果；`sentiment: null` 时必须显示“尚未启用”。
- 左侧“历史记录、数据统计、模型管理、系统设置”本轮只做导航占位，不增加后端业务接口。
- “帮助文档”和“关于我们”使用前端弹窗或静态说明，不新增后端接口。

## 3. 技术方案

### 3.1 技术栈

- 后端：保留 FastAPI、Uvicorn 和现有 Python 推理服务。
- 前端：原生 HTML5、CSS3、JavaScript（ES6+），不引入 React、Vue、Node 或 CDN 依赖。
- 图标：优先使用内联 SVG；不得依赖联网字体或第三方图标站。
- 字体：系统字体栈，优先 `Microsoft YaHei`、`PingFang SC`、`Noto Sans CJK SC`。
- 测试：保留现有 Python 测试体系；前端核心状态转换应拆成可测试的纯函数或通过 DOM 行为测试验证。

选择同源静态页面的原因：答辩环境可离线运行，不需要单独启动前端开发服务器，不产生跨域配置，并能直接复用现有 `/api/*`。

### 3.2 推荐目录

```text
src/web/
├── __init__.py
├── app.py
├── config.py
├── errors.py
├── service.py
├── static/
│   ├── css/
│   │   └── app.css
│   ├── js/
│   │   └── app.js
│   └── images/              # 仅放必要的本地图片；图标优先内联 SVG
└── templates/
    └── index.html

tests/
├── test_web.py              # 现有 API 测试
└── test_web_frontend.py     # 首页与静态资源测试
```
### 3.3 服务端集成方式

在现有 `create_app()` 中：

1. 挂载 `/static` 到 `src/web/static/`。
2. 新增 `GET /`，返回 `templates/index.html`。
3. 所有路径必须用 `Path(__file__)` 推导，禁止个人绝对路径。
4. 保持 `/docs` 和现有三个 `/api/*` 端点可用。
5. 不改变现有 API 响应体，不在后端拼接页面展示文字。

页面与 API 同源，因此前端请求使用相对路径 `/api/health`、`/api/categories`、`/api/predict`。

## 4. 页面信息架构

页面采用“顶部栏 + 左侧导航 + 主工作区”的桌面仪表盘布局。

```text
┌──────────────────────────────────────────────────────────────────┐
│ Logo + EcomNLU · 智购感知        服务状态  帮助文档  关于我们  设置 │
├──────────────┬───────────────────────────────────────────────────┤
│ 智能分析     │ 输入评论                   │ 预测类别              │
│ 历史记录     │ Top-K                      │ Top-K 概率             │
│ 数据统计     │ 开始分析 / 清空            │ 情感分析              │
│ 模型管理     ├────────────────────────────┴───────────────────────┤
│ 系统设置     │ 建议处理方式 / 接口详情                            │
└──────────────┴───────────────────────────────────────────────────┘
```

### 4.1 顶部栏

- 左侧：蓝色柱状图标、系统名称“EcomNLU · 智购感知”。
- 右侧：服务状态胶囊、帮助文档、关于我们、设置图标。
- 服务状态来自 `/api/health`，不可写死：
  - HTTP 200 且 `status=ok`：绿色圆点，“服务正常”。
  - HTTP 503 且返回合法健康响应：橙色圆点，“模型未就绪”。
  - 网络错误或非法响应：红色圆点，“服务异常”。
- 点击帮助文档：展示输入限制、Top-K 含义和错误说明。
- 点击关于我们：展示项目任务、10 类范围和团队分工摘要。
- 设置图标本轮显示“功能规划中”，不得出现无响应按钮。

### 4.2 左侧导航

- “智能分析”为默认激活项。
- “历史记录、数据统计、模型管理、系统设置”为禁用或规划中状态。
- 点击未实现项时显示轻量提示“该模块不在本轮 M6 演示范围内”，不跳转到空白页。
- 桌面端固定宽度约 216–232 px；小屏幕下折叠成横向或抽屉导航。

### 4.3 评论输入卡片

- 标题：“输入电商评论”。
- 多行文本框：允许输入最多 2000 个字符，具体上限必须由项目配置/当前契约保持一致。
- 默认使用 placeholder，不预填结果；可使用“例如：这款手机很好用，电池耐用，拍照也很清晰。”。
- 右下角实时显示 `当前字符数 / 2000`。
- Top-K 下拉框提供 1–10，默认 3。
- “开始分析”为主按钮，“清空”为次按钮。
- 请求进行中时：主按钮显示“分析中…”，禁用重复提交，输入区和 Top-K 保持可见。
- 支持 `Ctrl + Enter` 提交；不得仅依靠键盘操作。
- 清空按钮需要清除输入、错误和预测结果，并恢复初始空状态。

### 4.4 预测类别卡片

无结果时显示引导空状态：“输入评论并开始分析后显示结果”。成功后显示：

- 预测类别：使用 `category.label`，大号蓝色文字。
- 置信度：使用 `category.confidence`，格式化为百分比，保留 1 位小数。
- 使用模型：使用 `model_name`，禁止写死为 BERT。
- 推理耗时：使用 `elapsed_ms`，展示为 `12.4 ms` 一类格式。
- 若置信度为空、非数值或超出 0–1，应进入响应异常处理，而不是展示错误百分比。

### 4.5 Top-K 概率卡片

- 标题：“Top-K 概率”，K 应与当前选择一致，例如“Top-3 概率”。
- 严格按 API 返回数组顺序展示。
- 每行包含类别名、横向概率条、百分比。
- 概率条宽度按 0–1 映射为 0%–100%，并对 DOM 样式值做边界保护。
- 主类别使用深蓝色，其余使用浅蓝色；不得用颜色作为唯一信息载体。
- 空状态和错误状态下不得保留上一次结果，防止用户误认旧结果为本次输出。

### 4.6 情感分析卡片

- `sentiment === null`：显示灰色状态“尚未启用”，副文案“完成 M5 后开放”。
- M5 完成后若返回对象：
  - 标签只能显示“正向”或“负向”。
  - 同时显示置信度百分比。
  - 正向使用绿色，负向使用橙红色；仍需保留文字标签。
- 前端不得根据评论内容自行推断情感。

### 4.7 建议处理方式卡片

建议是**前端确定性映射**，用于答辩展示，不是模型预测。文案必须标注为“规则建议”。推荐映射：

| 类别 | 建议处理方式 |
| --- | --- |
| 书籍 | 转交图书售后团队 |
| 平板 | 转交数码产品售后团队 |
| 手机 | 转交手机售后团队 |
| 水果 | 转交生鲜售后团队 |
| 洗发水 | 转交个护售后团队 |
| 热水器 | 转交家电售后团队 |
| 蒙牛 | 转交食品饮料售后团队 |
| 衣服 | 转交服装售后团队 |
| 计算机 | 转交计算机售后团队 |
| 酒店 | 转交酒店服务团队 |

优先级规则：

- `sentiment.label === "负向"`：显示“优先级：较高”。
- 情感未启用或正向：显示“优先级：普通”。

这只是展示规则，不写入 `/api/predict` 响应，也不声称来自训练模型。

### 4.8 接口详情折叠区

- 默认折叠。
- 展开后显示本次请求摘要与响应 JSON，便于答辩解释前后端联调。
- JSON 必须来自本次真实请求；不显示 Python 堆栈、文件系统路径或敏感环境变量。
- 对长文本仅显示必要摘要，避免撑坏页面。

## 5. 视觉规范

### 5.1 风格

- 整体：浅灰蓝背景、白色卡片、蓝色主色、轻阴影、圆角仪表盘风格。
- 主色：建议 `#1769F5`；深色标题：`#10254A`；正文：`#334A6B`。
- 成功色：`#16A66A`；警告色：`#D98B19`；错误色：`#D64545`。
- 页面背景：`#F3F7FC`；边框：`#DCE6F3`。
- 卡片圆角：12–16 px；按钮圆角：8–10 px。
- 使用 CSS 变量集中定义颜色、间距、圆角和阴影。

### 5.2 响应式

- ≥ 1200 px：还原概念图的左右双栏主区域。
- 768–1199 px：左侧导航缩窄，输入与结果可保持双栏或根据空间变单栏。
- < 768 px：导航折叠，所有卡片单列，按钮可上下排列。
- 页面不得出现横向滚动条；概率条和长模型名必须可收缩或换行。

### 5.3 可访问性

- 所有按钮、链接、下拉框、文本框有可识别标签。
- 键盘焦点有明显轮廓。
- 异步状态使用 `aria-live` 通知。
- 图标按钮必须有 `aria-label`。
- 正文与背景保持足够对比度，状态不能只靠颜色表达。
- 支持用户的 `prefers-reduced-motion` 设置。

## 6. 前端交互与状态机

前端至少维护以下状态：

| 状态 | 界面行为 |
| --- | --- |
| `initial` | 显示空状态，允许输入 |
| `health-checking` | 顶部显示“检查中” |
| `ready` | 服务正常，允许提交 |
| `degraded` | 模型未就绪，保留页面但预测按钮不可用或提交后明确提示 |
| `submitting` | 按钮禁用并显示分析中，防止重复请求 |
| `success` | 清除旧错误并渲染本次结果 |
| `validation-error` | 聚焦相关输入并显示友好错误 |
| `server-error` | 清除旧结果，显示可重试错误 |

页面加载流程：

1. DOM 初始化并绑定事件。
2. 并行请求 `/api/health` 和 `/api/categories`。
3. 渲染服务状态并校验类别列表。
4. 用户提交前进行最小客户端校验。
5. 调用 `/api/predict`。
6. 仅在响应结构合法时渲染结果，否则显示“服务响应格式异常”。

客户端校验不是后端校验的替代。后端仍须保留全部契约校验。

## 7. API 对接规范

### 7.1 健康检查

```http
GET /api/health
```

前端必须接受健康检查的 503 响应并读取其中的合法 JSON；不能简单把所有非 2xx 都归类为网络故障。

### 7.2 类别列表

```http
GET /api/categories
```

用于校验返回类别与页面可展示范围。页面不得另建一份会与配置漂移的类别列表；处理建议映射允许在前端维护，但若发现未知类别，显示通用建议“转交人工客服团队”。

### 7.3 预测

请求：

```json
{
  "review": "这款手机很好用，电池耐用，拍照也很清晰。",
  "top_k": 3
}
```

成功响应示例仅用于说明结构：

```json
{
  "category": {"label": "手机", "confidence": 0.932},
  "top_k": [
    {"label": "手机", "probability": 0.932},
    {"label": "平板", "probability": 0.041},
    {"label": "计算机", "probability": 0.017}
  ],
  "sentiment": null,
  "elapsed_ms": 12.4,
  "model_name": "bert_base_chinese"
}
```

### 7.4 错误码到界面文案

| API code | 前端处理 |
| --- | --- |
| `INVALID_JSON` | 显示“请求格式错误，请刷新页面后重试” |
| `MISSING_REVIEW` | 显示“请输入评论内容”并聚焦文本框 |
| `EMPTY_REVIEW` | 显示“评论内容不能为空”并聚焦文本框 |
| `REVIEW_TOO_LONG` | 显示“评论超过 2000 字符，请精简后重试” |
| `INVALID_TOP_K` | 显示“Top-K 必须是 1 到 10 的整数” |
| `MODEL_NOT_LOADED` | 顶部切换为“模型未就绪”，显示启动模型的提示 |
| `INTERNAL_ERROR` | 显示“服务内部错误，请稍后重试” |
| 未知 code / 网络错误 | 显示通用错误，不暴露内部细节 |

错误文案优先使用 API 返回的 `message`，但前端必须安全地以纯文本写入 DOM，禁止使用未清洗的 `innerHTML`。

## 8. 安全与健壮性要求

- 所有用户输入与 API 文本使用 `textContent` 或等价安全方式渲染，防止 XSS。
- 不在浏览器控制台记录完整评论、密钥、环境变量或内部堆栈。
- 不使用 `eval`、内联事件处理器或动态执行字符串。
- 对 `fetch` 增加超时控制（建议 15 秒）和可重试提示。
- 新请求开始时清除旧结果；请求失败不得继续展示上一条预测。
- 不吞掉错误；用户看到友好信息，开发日志保留必要上下文。
- 不修改模型加载一次的后端约束。
- 不提交模型文件、数据文件、`.env`、缓存或生成日志。
